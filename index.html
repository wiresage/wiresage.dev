wiresage.dev

Open foundations for AI in networking and security.

Abstract. WireSage is an open-source community developing the shared infrastructure for applying large language models to networking and cybersecurity: MCP servers, agents, scanners and automation, together with the evaluations that show whether they work. Code, design discussions and results are public and permissively licensed, with typed tools, safe defaults and documented behaviour that anyone can read, test and reproduce.

Keywords: open source · MCP · network automation · cybersecurity · LLM agents · reproducibility

§1

Motivation

Networks and security tools are documented in RFCs, vendor manuals and decades of CLI habit. Language models read all of it fluently, but reading is not operating, and neither is defending. Handing a model a raw shell on production infrastructure is neither safe nor reproducible.

Our working hypothesis is that the gap is an interface problem, not a model problem. Give models small, typed, well-described tools that mirror what a careful engineer would do, and they become useful colleagues instead of risky ones. WireSage exists to build those interfaces in public, and to measure whether they work.

Because the stakes are operational, the work has to be inspectable. An open foundation lets engineers, researchers and vendors audit the tools, rerun the experiments and disagree with the results.

2.1Open problems

  • P1Vendor-neutral tools

    One tool vocabulary shared across platforms, so an agent learns a task once.

  • P2Change review

    Agents that read a configuration diff, explain its blast radius and ask before applying it.

  • P3Evidence-first scanning

    Findings a model triages, with the raw output attached to every claim.

  • P4Untrusted tool output

    Logs, banners and packet captures are attacker-controlled input. How should tools sanitise what a model reads?

  • P5Least-privilege agents

    Scoped credentials, read-only by default, and an audit trail for every call.

  • P6Reproducible evaluation

    Open benchmarks and lab topologies that measure how well models actually operate networks.

These are directions, not promises. Each one starts as a public discussion.

§3

Method

Design rules every WireSage project is held to.

3.1Typed tools, not raw shells

Every capability is a named tool with a schema the server validates before anything reaches a device.

3.2Reversible by default

Risky changes run inside rollback-capable sessions where the platform allows it, so a lost connection undoes the change instead of locking you out.

3.3Credentials stay local

The model sees tool names and results. Passwords, keys and sessions never leave the server.

3.4Small context, local-first

Tool sets can be scoped by category, so smaller self-hosted models fit and nothing has to leave your network.

3.5Documented and inspectable

Every tool is listed in a public reference and can be called by hand, so behaviour can be checked, not assumed.

3.6Threat model first

Tool output is treated as untrusted input, and every project states what it assumes an attacker can do.

§4

Openness

Commitments we hold ourselves to, and welcome being held to.
Code
Every repository is public under a permissive license.
Process
Issues, design discussions and roadmaps happen in the open.
Results
Evaluations publish their method, data and scripts so anyone can rerun them.
Security
Vulnerabilities are reported privately and disclosed responsibly. Tools default to read-only where they can.
Governance
Decisions are made in public by contributors. No single vendor owns the roadmap.
Independence
WireSage is not affiliated with any vendor whose tools its projects integrate.
§5

Contribute

Maintained by volunteers. Every contribution size counts.

From a bug report with the platform version attached, to a new server for a tool we haven’t touched yet, to a lab topology for the benchmark: contributions are how this work moves forward.

  1. Use a project and report what breaks

    Include the device or tool, its version and the exact tool call.

  2. Pick up an issue

    Look for good first issue labels across the organization.

  3. Propose an integration or a question

    Open a discussion describing the platform, its API and what “safe” means there.
